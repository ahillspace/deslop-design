# Dashboards and internal tools

Use when someone repeatedly monitors, decides, or changes operational state.
Start from their most frequent task, urgent exception, and next action.
Show active filters, time range/timezone, freshness, and the scope of summaries.
A welcome panel or KPI strip earns space only if it helps that work.
Use domain vocabulary, purposeful density, aligned numerals, and meaningful status emphasis for character.
Preserve familiar navigation and control behavior.

Distinguish zero, missing, not applicable, stale, loading, and failed data.
Ensure filters and sorts update both detail and summaries consistently, or label their different scopes.
Keep selection and action targets clear across pagination and filtering.
For mutations, define pending, success, failure, retry, and duplicate-submission behavior.
Claim persistence, recovery, or undo only when implemented.
Explain unavailable actions and preserve user input on failure when the system supports it.

Reuse existing components and native semantics before adding complex controls.
A custom appearance does not justify rebuilding keyboard navigation, focus management, or announcements.
Show status through text or shape as well as color.
Choose touch targets for the usage scene; do not mislabel a preferred 44px target as the universal WCAG AA minimum.

At narrow widths prioritize the same essential task, keeping critical columns/actions available through a deliberate layout or usable scroll region.
Verify the complete task, filter reset/no results, slow or failed data, long labels, keyboard use, and any relevant save/retry path.
A static prototype must label simulated actions and state what is not connected.
